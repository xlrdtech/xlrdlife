The nest

tmux SERVER                    one background process, holds everything
└── SESSION  "xen"             what you attach to / detach from
    ├── WINDOW 0  "bash"       a tab — full screen inside the session
    │   └── PANE  %0           bash
    └── WINDOW 1  "2.1.220"
        └── PANE  %1           Claude  ← your canonical inject target
LevelWhat it actually isYours
ServerOne process per user. Holds every session. Dies only on kill-server or reboot.one
SessionWhat you attach and detach from. Survives closing the terminal.xen
WindowA tab. Full-screen within the session.0, 1
PaneA split inside a window. Runs one program.%0, %1

The trap that keeps biting

"Pane zero" is not a unique address. Every window has a pane 0. Yours are xen:0.0 and xen:1.0 — both are "pane zero," in different windows. Only the pane ID is unique server-wide: %0 and %1, never reused while the server runs.

This is why pinning the inject lane to a position keeps going stale, and why the fix was to identify the target by what's running inside it instead: the pane whose process tree contains a live Claude, inside session xen.

What a stray line in bash actually means — and it's fine. Pane %0 shows -bash: 3:46:39: command not found from a 3:46:39 PM voice line. That is expected, not a leak: the injector fans out to primary / secondary / tertiary pane sentinels, so a non-Claude pane will sometimes catch a copy. Bash can't interpret it, says so, and nothing breaks. The Claude pane received the same line correctly.

Useful to know when reading a pane: a "command not found" in %0 is not evidence of misrouting. The real check is whether %1 got it.

Address forms, and which to trust

FormMeansStable?
%1Pane ID — globally unique✅ for the life of the server
xen:1.0session : window . pane-index⚠️ shifts if windows are renumbered
1 or 0.0ambiguous — index only❌ never trust for routing
Detaching kills nothing. The server keeps the session and every pane running when you close the terminal. That's why Claude survives, and why the right way to reconnect is new-session -A -s xen — attach if it exists, create only if it doesn't. Making a fresh session per login is what caused the pane pins to go stale in the first place.

Useful commands

tmux ls                          list sessions
tmux new-session -A -s xen       attach to xen, create only if missing
tmux list-panes -a -F "#{pane_id} #{pane_current_command}"
tmux capture-pane -p -t %1       dump what a pane is showing
Ctrl-b d                         detach (leaves everything running)
Ctrl-b w                         window picker
