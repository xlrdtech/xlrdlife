The headline

Sessions can message each other

2.1.224

Native cross-session messaging replaces hand relay

A session sends another session a summary — not history, not files — and the receiver picks it up mid-task. It works both directions, across machines, and a session can initiate on its own when a change it made affects what another session is doing. Discovery is via ListAgents. macOS and Linux.

  • addedcrossSessionInbound and dialogExpiry — messages into a bypassed-permissions session are held for approval; outbound auto-delivers
  • addedclaude self-hosted-runner — your own machines or containers host web, mobile and desktop sessions (Team/Enterprise)
  • addedarchive plugin source — install from a zip over HTTPS, no git or npm, with optional SHA-256 pinning
  • removedThe 200-subagent-per-session cap is gone — long sessions no longer refuse new agents
  • fixedSendMessage reported "Message sent" when the write had failed. Failed deliveries now surface as errors
  • securitySandbox deny entries with a trailing slash (denyRead: "~/.aws/") were silently bypassable on Linux and macOS
  • fixedLong project paths resolved into another project's session directory under a shared sanitized prefix
  • changedBash tool description now states outright that output goes to the model, not reliably to the user

Why it matters here

Three that land on this stack

1 — Cross-session messaging is the seat architecture, natively

Seats reporting up to one operator seat has been manual relay through tmux injects. This is that channel, built in, carrying a summary instead of a transcript.

2 — The SendMessage false-success fix

Reporting "sent" on a write that failed is the exact failure class worth fearing: a green reading that isn't. Same shape as a health endpoint returning an app shell, or an install exiting 0 having done nothing.

3 — The subagent cap is gone

Long-lived sessions that fan out repeatedly used to hit a wall at 200 and refuse new agents. Concurrency and depth limits still apply.
