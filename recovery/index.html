Captured Sat Aug 1 2026, 21:06 EDT · machine: Mac mini M4 · all facts below carry a VERIFIED or UNVERIFIED tag

This page exists so the next system death does not put you back to zero. It contains no secrets. It tells you where every secret lives, what it unlocks, and the order to move in. If you are reading this on a phone with nothing else, start at THE FIRST FIVE and do not read ahead.

verified = a command was run and the output was seen. unverified = inferred, not tested. broken = confirmed failing right now. Nothing on this page is a guess.

The first five things. In order.

Do these before reading anything else on this page. Do not improvise the order.

  1. Copy the M4 drive. Before you touch anything else.

    Everything is on one USB drive: /Volumes/M4. There is no backup of the code tree. Do not browse it, do not du it, do not open folders. Plug it into any working machine and start a resumable copy, then walk away.

    # resumable — safe to interrupt and re-run
rsync -aH --partial --append-verify --info=progress2 \
  /Volumes/M4/sync_/ /path/to/new/disk/sync_/

    verified tmutil destinationinfo → "No destinations configured." Syncthing runs but covers only the memory vault, not the code tree. If M4 dies mid-read, whatever you already copied is what you have — which is why the copy comes first and the reading comes second.

  2. Sign into 1Password. You need two things only you have.

    The master password and the Secret Key. Nobody — not Anthropic, not 1Password, not any agent — can recover these. If both are lost, 1,196 human logins are gone and the rebuild floor drops to "email-reset every account one at a time."

    verified Vault "xen" reachable via CLI v2.32.0 at /opt/homebrew/bin/op, driven by a service-account token (bare op whoami fails; the wrapper bin/xen-op loads the env file). 1,200 items: 1,196 LOGIN, 1 IDENTITY, 3 API_CREDENTIAL. The 3 API credentials are the vault's own service-account tokens. 1Password holds your human logins. It does not hold the machine tokens.

  3. Confirm the phone line is alive and in your hand.

    Most of the accounts on the recovery list use SMS 2FA delivered to a line that is itself on the recovery list. Pay it, port it, or physically hold the SIM — but resolve it before you start any account recovery, because a lapsed line makes every SMS-2FA account unrecoverable at the same moment.

    unverified — inferred from the account inventory, not from testing a lockout. Named here because it is the one failure that cascades across everything at once, and the fix (keep the line) is cheap while the line still works.

  4. Restore the machine tokens from your copy — not from 1Password.

    One file carries 41 machine tokens and sits on the critical path for voice. It is not in 1Password and it is not backed up anywhere else. Pull it off the copy you made in step 1. Its two apparent locations are the same file.

    File
    /Users/qi/.xen/secrets.env
    Same inode
    /Volumes/M4/sync_/exedus/dev_/xen/.xen-state/secrets.env
    Why
    ~/.xen is a symlink to .xen-state. One file, two paths — so there is one copy, not two.
    Consumed by
    bin/xen-reply-vvs line 27 — voice does not speak without it

    verified via os.path.samefile → True. If this file is lost, every one of the 41 tokens must be reissued individually from its own provider console. Nothing recovers it in bulk.

  5. Join the tailnet, then start the six load-bearing daemons.

    Tailscale first — it is how you reach the Hetzner box, and it is the only path to several services that are otherwise firewalled. Then bring up the six jobs in the table below, in any order. Everything else can stay down; those six are the system.

    verified tailnet xlrdtech@, 18 nodes, xen-hetzner active and direct. Do not start all 234 launchd jobs. Most are optional and several are actively broken — see "Open wounds."

The two storage facts that matter most. verified

  • M4 has no health signal. It is USB-attached and reports SMART Status: Not Supported. The single most important disk in the system cannot tell you it is failing. There will be no warning.
  • X31 and nitro2tb are exFAT, which has no journaling. One unclean unmount or power loss corrupts the directory table. Anything that exists only on those volumes is one bad unplug from gone. They are the failure mode, not the mitigation.

The canonical tree verified size unknown

/Volumes/M4/sync_/exedus/dev_/xen — 138 top-level directories.

Total size could not be measured. du -sh was started three times and never completed in over 20 minutes of wall clock. That non-result is the finding: the tree has enough small files that a full walk on USB is impractical. Measured fragments: .deploy/ = 6.8 G (several full git worktrees), node_modules/ = 227 M, media/ = 14 M.

Consequence for recovery: any plan that says "just copy the tree" needs a measured, resumable transfer. A single cp that fails at 80% leaves you with nothing you can trust. This is why step 1 uses rsync --partial --append-verify.

The memory vault — the one thing that already survives verified

/Volumes/M4/sync_/brain_/agents/xen/xen_memories — 19,460 markdown files, 39,921 files total, 21 G. MEMORY.md is live (112 lines, modified today).

Syncthing replicates this vault to 4 devices. Memory survives a disk death. Code and credentials do not. That asymmetry is the single highest-leverage thing to fix: add the xen code tree to the existing Syncthing config and the largest gap in the system closes with no new software and no cost.

None of the six has a watchdog. verified

A grep across both bin directories for those six labels returns exactly one file, and it is a restore script, not a runtime supervisor. 47 watchdog plists exist and they cover ADB, audio, panes, disk, browser, 2FA and cookies — none of them covers the critical path.

The cheapest real fix: one job that stats those six log paths and screams when any exceeds 3× its own interval. That is a dozen lines of shell and it closes the entire gap.

Single points of failure, ranked

Ordered by how much is lost when each one goes, not by how likely it is.

  1. The M4 volumeOne USB drive, no backup of the code tree, no SMART warning. Everything canonical. This is the exact shape of every prior ground-zero event.
  2. secrets.env41 machine tokens in one unbacked file on the critical voice path. Loss means reissuing each token from its own provider console, by hand.
  3. The 1Password service-account tokenLives on the boot disk, so it fails independently of M4 — one machine death can take the code tree and the automated vault access in one stroke. Currently world-readable at 0644.
  4. .claude.json wiring55 MCP servers' worth of configuration. Recoverable in principle, brutal to rebuild from memory under stress.
  5. Beeper single-identity concentrationEvery network routes through one account. One suspension takes all comms simultaneously.
  6. Per-persona Claude refresh tokensFour separate OAuth flows to redo, each needing a browser and a human.
  7. Gmail OAuthConsent screen re-approval, gated on the Google account, which is gated on 2FA, which is gated on the phone line.

Three corrections to what you remember

  • "No working SSH key" is stale. verified The July 9 lockout was real — an OS reinstall out of rescue wiped authorized_keys. But tailscale status right now shows xen-hetzner active and direct, with 1.0 GB transmitted. The box is up and reachable on the tailnet. A later note documents working ssh + docker exec over that same path.
  • "124 GB prone to fail" does not exist. verified No such figure appears anywhere in the tree. The real number is a 128 G sparse Windows disk image on a single non-RAID disk. The fragility is not capacity — it is that there is one disk, no RAID, and no snapshot. That is worse than being full.
  • Hetzner Cloud tooling will never see this box. verified hcloud server list returns zero servers, and console.hetzner.com does not show it. Recovery lives only at robot.hetzner.com. If you are ever locked out again, that is the only door.

Two open Hetzner items

1. Root compromise, contained but not resolved. verified A miner ran as root from July 9 at 399% CPU with self-rotating cron. The entry door was noVNC on :8006 published to the open internet with no auth. It was killed, persistence stripped, payloads preserved, load dropped 4.4 → 0.68, and the port is now tailnet-only and verified blocked from outside. A root compromise means rebuild. That decision is still open and it is yours.

2. Re-key prevention was never done. verified Two items sit unactioned: register the M4 public key in Robot → Key management so future reinstalls auto-inject it, and enable the Robot Webservice user so rescue and boot can be scripted. Until both exist, any reinstall repeats the July 9 lockout and the only recovery is a human driving a pixel KVM.

Open wounds

Things that are broken right now and will mislead you during a rebuild if you do not know about them.

The top-level watchdog is a corpse that reports success broken

com.exedus.xen-watchdog runs every 5 minutes and exits 0. It also: curls a port nothing listens on, kickstarts a service whose plist is disabled, kickstarts a second service that is not loaded, and calls two Python files that do not exist. Its own log says Final status: unreachable — and it still exits 0.

Anything relying on "the watchdog will catch it" is unprotected. Its intended replacement, xen-watchdog-v2, is sitting on disk unloaded.

Backup and log rotation have been dead for 34 days broken

com.exedus.xen-snapshot (hourly) and com.exedus.xen-log-rotate (15 min) are both loaded and both have not written in 34 days. Snapshot is the backup rung. In a system-death scenario it is the job that decides whether the baseline survives, and it has been silently not running for a month. Rotation being dead is why one log is pinned exactly at its 10 MB cap.

Fix these two before anything else on this list. They are the ones that make the next page like this one possible.

Other confirmed-bad state verified

  • 30 plists present but not loaded — dark rungs a rebuild would silently miss. Seven of them are the voice/audio recovery path, which means the audio auto-recovery commandment currently has no daemon behind it.
  • Two silence clusters, each from a single event. The omni family all stopped at the same moment 10.7 days ago; the bee family all stopped 13.2 days ago. That is two root causes, not nine failures.
  • A canon verifier is screaming and nobody is reading it — it reports a broken hardlink and diverged content, meaning a daemon is running stale code.
  • The telemetry backend is crash-looping on a database connection pool timeout.
  • Log paths on the boot disk. The orchestrator logs to /tmp and roughly 20 other jobs log to /tmp or ~. All of it is lost on a fresh machine. Only four comms jobs log onto M4.

The same door that got Hetzner rooted is open here unverified — check this first

A Cloudflare named tunnel publishes 37 hostnames to the public internet, all mapping to local ports on this Mac. Two of them are full control surfaces: the all-in-one MCP hub (documented in its own config as "no auth, open") and a web terminal. That is precisely the failure mode that got the Hetzner box compromised — a control surface published without auth.

A Cloudflare Access apply-script and a verification file both exist in the tree, so edge gating may be enforced. It was not verified — no external request was made during this audit.

This is the highest-value thing to check next, and the correct test is the one already learned the hard way on Hetzner: curl those hostnames from outside the tailnet and see what answers.

The floor

What cannot be recovered without you. This is the honest bottom of any rebuild.

No agent, no script, and no backup can do these

Everything above this line is a machine problem with a machine answer. Everything below it requires you, in person, with something only you have.

  • 1Password Secret Key — no reset exists, by design. Both are required together.

The one insight worth acting on today, while everything still works.

Most of the accounts on that list use SMS 2FA delivered to a phone line that is itself on that list. If the line lapses first, every SMS-2FA account becomes unrecoverable at the same moment — not one at a time, all at once. The list above is not seven independent problems. It is one problem with seven faces, and the face is the phone line.

unverified — inferred from the account inventory, not from testing a lockout. Stated plainly because the mitigation is free and the failure is total: move the critical accounts off SMS 2FA and onto TOTP codes stored in 1Password, so the phone line stops being the root of the tree.

If you only remember four things

  1. M4 is the only copy and it cannot warn you. USB-attached, no SMART. Copy it before you do anything else, every time.
  2. Memory survives; code and credentials do not. Syncthing already replicates the vault to 4 devices. Adding the code tree to that same config is the single highest-leverage fix available, and it costs nothing.
  3. 1Password holds your logins, not your machine tokens. Those 41 tokens live in one unbacked file. Until they are in the vault, a disk death means reissuing every one by hand.
  4. The phone line is the root of the 2FA tree. Protect it before you need it, or move off SMS entirely.
