Design brief · verified 2026-08-16

OmniP

Every device hears you. One hub remembers. A dead battery costs nothing.

Verdict — false

Snapcast runs the opposite direction

The claim under test: "run a snapclient on each machine to capture its audio and stream it to the central server." That is inverted. snapclient is a playback client — it decodes and plays, it never captures.

"Audio is captured by the server and routed to the connected clients. Several players can feed audio to the server in parallel and clients can be grouped to play the same audio stream." snapcast README, line 17
"Knowing the server's time, the chunk is played out using a system dependend low level audio API (e.g. ALSA) at the appropriate time." snapcast README, line 41

Snapcast is one source in, many speakers out — multiroom sync. OmniP needs many capturers in, one hub out. Installing snapclient on the Mac, the PC and the phone produces three devices playing the same audio out their speakers. Zero capture.

The steelman, stated honestly: snapserver does accept a tcp:// source, so remote machines can push PCM in. But it is one hand-configured port per sender with no discovery, and the meta combiner that sounds like a mixer is documented as "plays audio from the active source with the highest priority" — a failover selector. It would silently discard the redundant capture that is the entire point.

Keep Snapcast for the other leg. It is genuinely good at fanning one stream out to speakers everywhere — the listen from anywhere half of OmniP. It just cannot be the capture half.

The requirement, in his words

"Right now my context is getting fragmented because when one device dies that's connected to something enabling the transcription or audio injection, then there's a gap. It's really frustrating… The fallback shouldn't be 'grab another device that's charged.' The audio should be coming from everywhere. Omnipresence. And omni-awareness." 2026-08-16, 17:48–17:49

Two constraints ride alongside it: it must work across every platform, and desktop audio must not be required — "I want the desktop audio to be me, but it should not be required."

Per-platform capture

There is no single cross-platform capture API. The capture agent is per-platform; only the transport is shared. Anything claiming otherwise is describing a product that doesn't exist.

PlatformMechanismReality
macOSScreenCaptureKit capturesAudio (13.0+), or BlackHole 2chBoth available. BlackHole already installed.
WindowsWASAPI loopback⚠ ffmpeg has no native WASAPI loopback input. -f dshow enumerates DirectShow sources, not render endpoints. Needs a small capture binary.
LinuxPipeWire / Pulse .monitor sourceStraightforward. Known but unverified here.
AndroidAudioPlaybackCapture (API 29+)⚠ Requires a MediaProjection consent tap per session. Use AudioRecord mic capture in a foreground service instead — one grant, ever.
iOSReplayKit broadcast extension⚠ No system-audio capture exists. RPSampleBufferType.audioApp is app audio only — AVPlayer, Safari video and Music are all uncapturable. Broadcast must be started by hand from Control Center.

iOS is a real hole, not a skipped step. The honest version: the iPhone can be a listener, not a capturer, without a signed app built for the purpose. The practical always-on iOS node is microphone capture from an app with the background-audio mode — it hears the room, runs unattended, needs no per-session tap.

Transport — WebSocket carrying Opus, over Tailscale

Evaluated against the constraint that this must be free, self-hosted, always-on, and survive a node dying mid-sentence.

CandidateVerdict
WebSocket + Opus✅ Recommended. First-party client on every platform. Many-to-one is its default shape — one port, N connections, dynamic join. TCP rides Tailscale with zero NAT work.
SRTStrong runner-up — reconnect and ARQ built in, already compiled into his ffmpeg. Weak on mobile.
RTPPort-or-SSRC per sender, no reconnect, UDP loss degrades STT.
LiveKitApache-2.0 and self-hostable, but a conferencing SFU with recording bolted on. Heavy for one-way audio.
Raw PCM over TCP256 kbps/node vs ~24 kbps for Opus, for zero benefit.

Each message is a header plus one Opus packet. The header carries node_id, seq, t_capture, and capture_source. The timestamp is not decoration — it is the entire basis of dedupe.

Reconnect is where the whole requirement lives: a dying node isn't a crash, it's a reconnect loop with a monotonic sequence number, so the hub knows exactly what it missed.

The hub

N nodes→one listener→per-node archive→per-node STT→align→merge + vote

Never mix at the audio level for the archive. Mixing destroys attribution and makes dedupe impossible. Mix only for live monitoring. Each node gets its own segmented Opus on disk plus a JSONL index.

Auto room-grouping, no config

A rolling energy-envelope fingerprint per node, cross-correlated pairwise. High correlation at small constant lag means same acoustic space. It detects co-presence automatically — which matters because these devices move with him.

Dedupe — merge, never drop

  1. Independent STT per node. Never transcribe a mix. N streams, N transcript tracks.
  2. Align same-room segments on the common clock, ±1.5s jitter window.
  3. Score token-set similarity over the overlap. Above threshold means the same utterance heard twice.
  4. Merge into one canonical utterance carrying heard_by: [node_a, node_b, …], each node's raw text and confidence retained. Canonical text by word-level vote across all N — never by taking the highest-confidence transcript wholesale.
The part nobody mentions

Redundancy is an accuracy win, not just a reliability win. Two microphones voting produce a better transcript than either alone. You are not paying a cost for the overlap — you are buying error-rate reduction with it.

Why this closes the actual gap

Because the merged timeline carries heard_by, a node dying produces no discontinuity — the utterance survives from the other node, and downstream context sees unbroken speech. A real gap exists only when heard_by reaches zero, and that is now a precise detectable event rather than a silence discovered hours later.

Coverage watchdog

Continuously tracks how many nodes currently hear him.

  • Runs on its own schedule, never on a prompt.
  • Announces only on state change — the transition to coverage == 1 is the pre-failure warning: you are now one device away from a gap. Narrating every healthy tick trains him to ignore it, which is how the real alarm gets missed.
  • Asserts on artifacts: per-node last-audio-frame timestamp, battery percentage, segment file mtime. Never "the process is up."

Battery telemetry belongs inside this watchdog, not beside it. The described failure is substantially a charge-state problem, so charge state is a first-class mesh signal.

First step

The M4 is the hub, not a required capture source — which is exactly the constraint that desktop audio be him, not a dependency.

  1. Stand up the hub listener on the M4's tailnet address, speaking the frame format above, writing per-node segmented archives plus a JSONL index.
  2. Make the M4 the first capture node, to close the loop end-to-end with one node before a second device exists:
ffmpeg -f avfoundation -i ":1" -ac 1 -ar 16000 \
       -c:a libopus -b:a 24k -f ogg <hub-url>

:1 is BlackHole — routed desktop audio. Room audio is :6 (in), which raises the open blocker below.

Second node is the phone, mic-capture path — because that is the node that proves the design. Mobile, moves with him, battery-limited. The exact failure he described.

Open blocker

The M4 is a Mac mini with no built-in microphone. ffmpeg does enumerate an in device at index 6, but what physical input backs it is unverified. That needs eyes on the hardware — it determines whether the M4 can be a room-capture node at all, or is hub-only.
