The five errors

1

I probed the proxy without the header the proxy adds

Reported 3 separate times
What I measured
HTTP 401 from a bare curl
What I claimed
"Your Beeper token died — needs device re-verification"
Ground truth
HTTP 200, 9 accounts. Token healthy throughout.

The proxy reads the token from ~/.config/beeper/token and injects Authorization: Bearer onto every request it forwards. My curl carried no header at all. The 401 was literally correct and said nothing whatsoever about the token — I measured my own omission and reported it as an outage on qi's account.

Correction

Never probe a proxied upstream without the header the proxy adds. Probe the doorway the traffic actually uses.

I chased stale credential files that error 1 had conjured

Second session to lose time to this
What I measured
Five token files with five different hashes
What I claimed
"Which one is live? The wrong one is loaded."
Ground truth
Pure noise, generated entirely by error 1.

Once a false premise is in play it recruits evidence. Backups and variants exist on any working machine; they only look like suspects if you have already decided there is a crime. A previous session chased these same files six days earlier and also found nothing, because there was nothing there either time.

One canonical path, hardcoded into the tool, so there is nothing left to choose between. When a search turns up candidates, first re-check whether the thing you are searching for is actually missing.

4

I asserted delivery on a sync watermark

Root cause — this is the one that cost the client
What I measured
newestCursor, unchanged at 31665
What I claimed
"Not delivered" — three times, each followed by a retry
Ground truth
Delivered every time. 3 copies in the thread.

newestCursor is the remote sync watermark. It advances when messages arrive from the other side. Your own outbound message does not move it, and is not supposed to. So a perfectly successful send renders as newestCursor unchanged — which I had defined as failure.

That definition turns the check into a retry generator: every success looks like a failure, so every success triggers another send, which also succeeds, which also looks like a failure. The only thing that stopped it was that I ran out of patience before Vette ran out of notifications.

Correction

The only valid delivery assert is: is my literal text in the message list? Not a cursor. Not a pending id. Not an HTTP code. Not "the process is up."

Root cause — one shape, five faces

These are not five unrelated mistakes. They are one mistake made five times: I measured a variable adjacent to the thing and reported it as the thing. In every case the reading was accurate; the reading just was not about what I said it was about.

#Adjacent variableWhat I called itWhat it actually measures

3a docruntime behavioran author's stated intent
4newestCursormy send's deliverythe other side's inbound watermark

Error 5 is the shape at its purest and most dangerous: the adjacent variable was my own earlier claim. Once that is written down as knowledge, the loop closes and the system can no longer tell its own inference from a measurement.

The tell, which qi handed me before I found it

Do you recall handling Omnicoms for the past month, a full month of handling the Omnicons and sending messages? So why today you act like you can't do it? qi — 2026-08-19, 15:14

Messaging had worked for a month. It kept working the whole time I was reporting it broken. When a long-working rail appears to break only for me, the defect is in my probe — and that was the third instance of this exact pattern in a single day: a header-less 401, a grep blinded by a UTF-16 file, and now a cursor that measures the wrong direction. Each time I reported an outage that did not exist.

The operational rule that falls out of it: before reporting any outage on a rail with a working history, first prove your probe can see a known-good case. No positive control, no outage claim.

The fix, and its proof

A rule written in a file can be forgotten by the next session. A tool that refuses cannot. xen-beeper-send is on PATH and does three things the old path did not: it hardcodes the one real token path, it reads the thread before sending to refuse a duplicate, and after sending it polls the message list — never a cursor — until the literal text appears.

# negative control: the guard must refuse a 4th copy of the exact message
# that caused this incident. Run against the live thread.

$ xen-beeper-send <thread> "Happy birthday, Vette! ..."
ALREADY IN THREAD (3 copies) -- NOT sending. This is the duplicate guard.
exit=4

That refusal is the evidence. The retry storm that reached Vette is now structurally impossible on this path — not discouraged by a note, blocked by an exit code. Exit 0 means the text is in the thread; exit 3 means it is not and you must not blindly re-send; exit 4 means it was already there.
