The finding hiding in those two columns

deliv and accpt split the networks cleanly in two, and it is not a reliability split — it is two bridge architectures.

  • Facebook, Google Voice, WhatsApp echo your own message back into the room, so a read-back confirms it within seconds → DELIVERED.
  • Telegram, Google Messages, Instagram, LinkedIn, Slack accept with an id but never echo, so the text is absent on read-back → ACCEPTED.

Which means a read-back verdict partly measures whether the bridge talks back, not whether the message arrived. The honest primitive is the pendingID the API returns, resolved via message.upserted — not searching a thread for your own text.

What the duplicate guard cost and bought

  • 1 duplicate — one thread, two copies. Cause: a read-back taken too early reported 31 sends missing when they had landed, so their guard entries were cleared and one re-sent.
  • 0 duplicates across the 222-thread resume pass — 192 ALREADY_SENT + 30 UNKNOWN_INFLIGHT, zero new sends.
  • Fixed: http=0 is ambiguous by construction — the request left, the response was lost. It now stays marked and is never auto-retried. Assume-sent strands a message; assume-failed duplicates it. Only the destination knows, and only after it settles.

Also measured

  • /v1/chats paginates on cursor + direction, not nextCursor — 25 chats vs the real 300.
  • Every chat is a Matrix room underneath: !room:server with the network in the homeserver suffix. Nine networks, one addressing plane.
  • 32 concurrent senders saturate the Beeper desktop IPC (31 timeouts); it answers in 8 ms at 6.
  • Participants carry an isSelf flag — the authoritative identity signal. A thread with no non-self participant still is not automatically his: one such thread was another person entirely.
