SMS dedup returns "delivered" for messages it suppressed — and can mute one forever

Silent Verified

In beside-send.sh, a dedup hit refreshes the timestamp at line 75 and then exit 0 at line 76. The caller reads exit 0 and records a successful send. Worse: because the ten-minute window slides forward on every hit, any repeating identical message re-attempted inside that window is suppressed indefinitely. A recurring alert fires exactly once and is silently muted from then on.

Scale
Current log window: 2,496 dedup skips against 12,692 sends, with 3,478 live keys in /tmp/xen-beside-dedup that are never pruned.
Costs
Roughly one in six "sent" SMS never reached qi's phone, and every one of them was logged as a success.
Whose hands
Mine
One step
Stop refreshing the timestamp on a dedup hit — delete the touch at beside-send.sh:75 so the window expires on schedule instead of sliding forever.

Costs

Whose hands
Mine

What this page does not claim

Scope of the probe

Send was never exercised

No message was sent on any rail during this audit. Every statement about send capability is inferred from provisioning data and per-chat permission flags, never from a delivered message. The strongest honest claim is: 288 of 301 chats are marked writable, and every account qi actually converses on is provisioned for sending. Whether a specific message would arrive is untested.

Bridge-level errors are not evidence of breakage

Three bridges return a 502 on the capabilities endpoint and six cloud bridges return a 500. That is not proof of a dead rail. Google Voice throws the 502 while simultaneously carrying 43 healthy chats, a message three hours old, and a fully populated per-chat capability object. It means only that the local bridge does not implement that one endpoint. The trustworthy send signal is per-chat, not per-bridge.

The outbound router is green, conditionally

The failure that blocked three sends earlier today is not reproducing — four of four test completions succeeded on the first attempt. The root cause was an upstream rejection of the default request identity, and the fix depends on that identity staying correct. Two caveats stand: the fix is fragile in that specific way, and there is no endpoint that reports pool health without consuming a real completion, so the pool cannot be monitored cheaply. That is the remaining hole.

Nothing was touched

  • No messages sent, no chats started, no replies drafted.
  • No daemon restarted, stopped, or reloaded — including the duplicate speech worker.
  • No authentication flow run, no account connected or removed.
  • No credential value read, printed, or copied anywhere. This page contains none.
