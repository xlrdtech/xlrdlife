The 30-second version

Three components survived. Four were cut. Docker is not required — the venv is the whole environment. Screen work routes DOM-first to Stagehand, falls back to pixels via OmniParser, then acts through xen-computer-use. And the shell is registered as an OpenAI-compatible provider, which turns every OpenAI client on the box into a remote control.

01The stack as built

Three surviving components, each doing exactly one job. Nothing here overlaps with anything else — that was the filter.

ComponentJobState
OmniParser V2

The router, plainly

screen work arrives
        |
        +-- DOM reachable over CDP?
        |        |
        |       YES  -->  Stagehand      (exact, CPU-speed, preferred)
        |        |
        |        NO  -->  OmniParser     (pixels, works on anything)
        |
        +-- either path returns THE SAME element schema
        |
        +-- an LLM reads that schema and picks an element
        |
        +-- act:  xen-computer-use  (click / type / hotkey)
                  or Open Interpreter for shell-shaped steps

DOM and pixels are not competitors, they are a fallback chain. DOM is faster and exact but blind to canvas, shadow DOM, virtualized lists, and anything behind an overlay — where it does not just fail, it silently returns the wrong thing. Pixels always work because pixels are what a person sees. So: try DOM, fall back to pixels, never run both.

The live router state is not a guess — xen-do backends reports what is actually wired versus missing, and prints which route it would take right now.

xen-do see                   what is on screen right now (auto-routes)
xen-do see --url <u>         look at a page (DOM path)
xen-do backends              what is actually wired vs missing
xen-do see --force-vision    skip the DOM, go straight to pixels

Honest latency — measured, not marketed

OmniParser is a 0.23B captioner. On this M4 it took over 6 minutes to parse one screenshot. That is the real MPS number, measured tonight. The 200-600ms figures published anywhere else are GPU numbers and do not apply to this machine.

This is exactly why the DOM path is preferred and the vision path is the fallback. Do not design a loop that parses pixels every step.

One thing that is easier here than expected

This display is 1:1, not Retina-scaled — a screenshot measures 1920x1080 against a 1920pt screen, scale factor exactly 1.00x. So there is no coordinate-doubling problem on this Mac. Pixels from the parser are pixels the clicker can use directly.

02The common element schema

This is the integration contract. It is the reason the fusion works at all: both the DOM path and the pixel path return the same shape, so the model deciding what to click never needs to know which backend produced it.

Coordinates come back as both normalized (0–1, as OmniParser emits) and absolute pixels, plus a precomputed center point. Converting at the call site is exactly where off-by-a-screen bugs come from, so it is done once, here.

{
  "image":  "/Volumes/M4/.../data/shot.png",
  "width":  1920,
  "height": 1080,
  "count":  47,
  "elements": [
    {
      "id":          0,
      "type":        "icon",
      "interactive": true,
      "text":        "Sign in",
      "bbox_norm":   [0.8203, 0.0417, 0.9109, 0.0741],
      "bbox_px":     [1575, 45, 1749, 80],
      "center_px":   [1662, 62]
    }
  ]
}
FieldMeaning
idIndex into this parse. Stable only within one parse — never cache it across screenshots.
typeElement class as the detector saw it (e.g. icon, text).
interactiveWhether the element is clickable. Filter on this before asking a model to choose.
textThe caption or extracted text — what the model actually reasons over.
bbox_normNormalized xyxy, 0–1. Resolution-independent.
bbox_pxAbsolute pixel xyxy against width/height.
center_pxThe point to click. A clicker needs one point, not a box.

Because the schema is the interface, no extra "computer use agent" model is needed in the middle. An LLM reads the element list and picks an id; the actor clicks its center_px. That is the entire loop.

xen-omniparse                    parse the current screen
xen-omniparse shot.png           parse an image file
xen-omniparse --json             machine-readable
xen-omniparse --find "sign in"   only matching elements

03What was cut, and why

This is the most useful section on the page. Each of these looked good on paper. Each was checked and rejected for a specific, durable reason. Read this before re-litigating any of them.

Ferret-UI 2 CUT

The weights were never released. Apple shipped Ferret-UI 1 only, in October 2024. There is nothing to download.

Even if there were: the license is CC BY-NC 4.0 — research-only, non-commercial, which rules it out for any paid work. The repo has been dead for 22 months.

Verdict: not a tradeoff. There is no artifact and no commercial license. Nothing to reconsider later.

OS-Atlas CUT

Two variants, both rejected for different reasons. OS-Atlas-Base duplicates the grounding OmniParser already does — pure overlap, no new capability. OS-Atlas-Pro is the actual action model, but it is roughly 15 months stale on a Qwen2-VL base, its code is CUDA-shaped, and there is no verified MPS path.

Licensed Apache-2.0, so it is legally fine. It is simply not worth the disk or the port.

Verdict: legal, just redundant and stale. If you revisit grounding models, go to Holo2 instead — see below.

Magentic-UI CUT

It is a browser orchestrator with its own multi-agent loop. It replaces a planner rather than plugging into one — wrong shape for a stack that already has a planner. It also requires Docker.

MIT licensed. And to correct a common misreading: its human-in-the-loop can be fully disabled — the paper says so explicitly. So the cut is about architectural shape, not about autonomy.

Verdict: cut for shape, not for autonomy. Do not re-open this thinking the HITL was the blocker.

OmniBox CUT

It is a Windows 11 VM in Docker whose only purpose is to give an agent a machine to look at. qi already has the machine — this Mac, his real browsers, his real logged-in sessions.

It is also structurally impossible here: KVM-dependent, and Microsoft's own note says it runs only on Windows and Linux. This is Apple Silicon, and Docker is not installed.

Verdict: solves a problem that does not exist here, and could not run if it did.

The one you were not told about — Holo2

Holo2 (H Company, Apache-2.0, November 2025, Qwen3-VL base) does both grounding and navigation. It is the best future upgrade path for this stack and the clear replacement to evaluate before any of the four cuts above get revisited.

UNVERIFIED: Holo2 has not been installed or benchmarked on this machine. Its MPS performance on a 24GB M4 is unknown. Treat it as the next experiment, not as a working component.

Licensing note worth keeping

The OmniParser LICENSE file is CC BY 4.0 — the MIT badge in its README is wrong. Both permit commercial use, so the stack is clear for paid work. The practical difference: CC BY carries no patent grant. Verified by reading the LICENSE file directly tonight.

04No Docker. At all.

Docker is not installed on this machine and is not required by anything in the stack.

Only two components ever wanted it — OmniBox and Magentic-UI — and both are cut, for reasons that have nothing to do with Docker. Cutting them removed the Docker dependency as a side effect, not as a compromise.

The environment is the venv

A Python venv at vendor/OmniParser/.venv holds everything the vision path needs. That is the whole isolation story. No daemon, no images, no layers, no VM.

AGPL cleanup, verified: the AGPL ultralytics package was removed, and import ultralytics now fails with ModuleNotFoundError — which is the correct result. The MIT icon_detect_v3 YOLOv9 detector is used instead, with the older Ultralytics-built icon_detect only as a fallback if v3 is absent.

05Shell as a model provider

qi's own idea, and the sharpest thing in the stack.

Provider vs tool — the distinction that makes it work

A tool is something a model decides to call. There is still a model in the loop, still a prompt, still an integration written for each tool, still a chance the model declines.

A provider is what the router routes to. It sits where an LLM would sit.

OmniRoute already runs on this box at 127.0.0.1:20128 and routes to providers by URL. Registering the shell as one more provider means a request carrying {"model": "tmux"} sends the prompt straight to the shell and returns stdout as the assistant message.

The consequence: every OpenAI-compatible client on the machine becomes a remote control for this Mac, with zero per-tool integration. Any app with a base-URL field and a model picker — and there are dozens — inherits shell access by pointing at it. Nothing has to be taught what tools exist.

base_url = http://127.0.0.1:20129/v1
model    = tmux        (or: shell)

Verified live tonight, all four:

  • The /v1/models endpoint lists tmux and shell, so client model pickers see them.
  • A request with no token returns 401.
  • A real command executed and returned its output with exit code 0.
  • rm -rf / was refused by the deny list.

⚠ Security — this is remote code execution by design

That is not a flaw, it is the entire feature. Which means the boundary has to be exact. Four controls, all live:

  • Loopback bind only. It binds 127.0.0.1 and refuses to bind anything else without an explicit override flag. Off-loopback, this endpoint hands the whole Mac to anyone who can reach the port.
  • Bearer token required. Generated on first run, mode 0600, never printed and never written to logs. Compared with a constant-time check.
  • Every command logged before it runs — append-only, so even a hang leaves a record.
  • Deny list for the catastrophic cases: rm -rf /, filesystem format, raw disk write to /dev/disk*, fork bomb, diskutil erase, and credential exfiltration (reading a secret and piping it off-box in one line).

NEVER expose port 20129 publicly. Not through a tunnel, not through a reverse proxy, not "just for a minute."

Be honest about what the deny list is: a guard against catastrophic accidents, not a security boundary. Any list like it is trivially bypassed with base64, $IFS, or aliases. The token and the loopback bind are the actual boundary.

Where the token lives

File: ~/.xen/runtime/shell-model.token — mode 0600, generated on first run.

The value is not printed here, is not in any log, and should never be pasted anywhere. Clients read it from that file at call time. If it is ever exposed, delete the file and restart the service to mint a new one.

OmniRoute reachability

OmniRoute is on 127.0.0.1:20128, loopback only. It is additionally reachable tailnet-only at https://<your-host>.ts.net:8443 via tailscale serve — which is private network access, not public exposure. Its API key location is a config field; the value is not reproduced on this page.

Rebuild from zero

  1. Clone OmniParser into vendor/OmniParser, create .venv inside it.
  2. Download the weights: huggingface-cli download microsoft/OmniParser-v2.0 --local-dir weights, then mv weights/icon_caption weights/icon_caption_florence. The parser's own preflight prints this exact fix if the weights are absent.
  3. Uninstall ultralytics from that venv — it is AGPL. Confirm with python -c "import ultralytics"; it must raise ModuleNotFoundError.
  4. Grant the terminal Screen Recording permission in System Settings → Privacy & Security, or screencapture silently returns nothing.
  5. Run xen-do backends. It names what is missing and what the current route would be.
  6. Start xen-shell-as-model.py. It mints the token on first run and prints its path, never its value.

One trap worth remembering — 64GB of RAM is not a GPU

Not part of this stack, but it cost real time this week. System RAM is not VRAM. Standard Hetzner cloud instances have no GPU at all; their GPU line is a separate, pricier product. SSH to both Hetzner hosts rejects the current key (Permission denied (publickey)), verified today, and that box has 124GB of storage against 20–50GB of weights for a single video stack.

The single command that settles GPU presence on any box: nvidia-smi. No output means no GPU. Run it before believing any spec sheet.
