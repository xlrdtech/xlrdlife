Two corrections worth keeping

Constant frame size means uncompressed, not Opus. The 321 B downlink was first read as Opus. That inference is backwards — Opus is variable-bitrate, so a constant frame size is evidence against it. 321 B is PCM, which the URL states outright with output_format=pcm_16000. The Opus side is the uplink. Rule of thumb: constant ⇒ uncompressed, variable ⇒ compressed.
An SDP rtpmap of 48000/2 is not proof of sample rate. RFC 7587 forces the Opus RTP clock to read 48000/2 always, whatever the real audio bandwidth. Checked here anyway: no maxplaybackrate, no sprop-maxcapturerate, no maxaveragebitrate anywhere in 3 MB of dump, and getStats reports "clockRate":48000 as genuinely negotiated. So the carrier leg really is 48 kHz fullband and the rate conversion is required after all.
It is a transcode, not a resample. You cannot resample Opus packets — same codec family on both sides is not a pass-through. Each leg must decode, resample, then re-encode: carrier Opus 48k → PCM 48k → PCM 16k → Opus 16k upward, and PCM 16k → PCM 48k → Opus 48k downward. Budget latency for it.

Consequences for a bridge

  • Google Voice is WebRTC over UDP/ICE, so call audio never appears in a HAR — a 34 MB capture held only JS bundles and signaling. Tap the audio device, not HTTP.
  • Carrier minptime=10 lines up exactly with the socket's 10 ms / 321 B frame.
  • useinbandfec=1 means Opus already covers packet loss — the bridge must not add its own retry layer.
  • The three rtcstats dumps are one call snapshotted three times, not three calls. Byte counts are identical across all three; only ICE counts grow. Do not treat them as independent samples.
  • 1,961–2,227 ICE host candidates in a single call — an enormous candidate set, and a plausible source of call-setup delay.
